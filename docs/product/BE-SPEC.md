# BE-SPEC

## 4.1 범위
카공지도 v0.x에는 서버가 없다.
데이터 경로는 정적 JSON 번들 하나로 닫힌다.
BE-SPEC은 서버 구현 제안이 아니라 데이터 경계와 전환점을 기록한다.
외부 API, DB, 로그인 서버는 비범위다.

## 4.2 데이터 경로 추적표
| 추적 | 항목 | 정의 | 상태 |
|---|---|---|---|
| B1 ← G2 | 시드 번들 진실원 | `app/src/data/cafes.json`은 보호 시드와 같은 스키마를 가진 정적 번들이다 | 구현됨 |
| B2 ← G2 | 시드 교체 절차 | 데이터 갱신은 JSON 교체 뒤 키 집합 검사와 코어 테스트 통과로만 인정한다 | 문서화됨 |
| B3 ← G3 | 장래 API 전환점 | 정적 로드 함수를 단일 진입점으로 유지해 추후 fetch 교체가 가능하게 한다 | 경계 정의 |

## 4.3 B1 시드 번들 진실원
앱 런타임은 `cafes.json`을 번들에 포함한다.
보호 시드는 테스트 기준선이고, 앱 번들은 실행 입력이다.
둘의 키 집합이 달라지면 필터, 정렬, 렌더가 같은 엔티티를 보지 않게 된다.
따라서 데이터 검증은 필드 존재만 보지 않고 양방향 집합 등가로 확인한다.

## 4.4 B2 교체 절차
시드 교체는 새 기능 구현이 아니다.
교체 절차는 보호 시드와 앱 번들의 키 집합을 확인하고, 기존 S1~S9 테스트를 다시 실행하는 것이다.
필드가 추가되면 먼저 ERD 확장 후보에서 CONFIRM을 해제해야 한다.
가격, 소음, 운영시간 상세 같은 항목은 교체 절차만으로 들어올 수 없다.

## 4.5 B3 API 전환점
장래에 서버 API가 필요해져도 현재 앱은 바로 fetch를 흩뿌리지 않는다.
데이터 로드 진입점을 한 곳으로 두면 정적 JSON에서 API로 바꾸는 범위가 좁아진다.
그러나 v0.x에서 서버를 만들지는 않는다.
현재 목표는 공부적합 순위와 필터의 기계 검증이지 데이터 수집 플랫폼이 아니다.

## 4.6 비범위
서버 라우팅, DB 스키마, 인증, 관리자 입력 도구는 지금 만들지 않는다.
실시간 혼잡도나 리뷰 수집도 비범위다.
경계 밖 기능을 넣으면 카공지도 핵심인 공부적합 비교 검증이 흐려진다.
